# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

SwarmAgents is a production PBFT-based distributed job scheduling system where agents reach consensus on job assignments using cost-based selection over gRPC, with Redis persistence.


**Remote test setup (deployment environment):**
- `ssh swarm` connects to the **database node** (runs Redis and orchestrates the run). This is the only host reached from the laptop; every other node in the topology is reached *from* it.
- On that node, become root with `sudo su -` before doing anything else: the code lives at `/root/SwarmAgents` and the passwordless SSH keys to the agent nodes belong to root, so neither is reachable as the login user.
- As root, the database node has **passwordless SSH to every other node in the topology**, which host the agent processes. All hostnames are pre-resolved in `/etc/hosts`, so use them directly — no IPs needed. The current slice is **`agent-1` … `agent-92`** (contiguous, verified 2026-09-09), each with a paired `agent-N-mon` monitoring host on a separate subnet. Earlier revisions of this file said `agent-40`; check `/etc/hosts` rather than trusting a written range.
- Agent ids map to sites in **contiguous blocks sharing a subnet**, so a site outage removes a solid id range: `agent-10`–`agent-18` is PSC, `agent-68`–`agent-74` is AMST. **Sweep reachability before sizing a run.** As of 2026-09-09 18:40 UTC, AMST is back and PSC is still down: **83 of 92 up**, which is still short of the ~90 VMs every rung above Hier-30 needs (90 at 1/VM, 180 at 2/VM, 270 at 3/VM) — PSC's 9 nodes are the whole remaining gap.
  ```bash
  seq 1 92 | xargs -P 40 -I{} bash -c '
    out=$(ssh -o BatchMode=yes -o ConnectTimeout=6 -o StrictHostKeyChecking=accept-new agent-{} hostname 2>&1)
    if [ $? -eq 0 ]; then echo "UP agent-{}";
    elif echo "$out" | grep -qi "host key"; then echo "KEY agent-{}";
    else echo "DOWN agent-{}"; fi'
  ```
  **`StrictHostKeyChecking=accept-new` is not optional here.** A host that returns from a rebuild has a new host key, and plain `ssh` under `BatchMode` then fails with "Host key verification failed" — indistinguishable from a timeout in a pass/fail sweep. That is exactly how AMST was recorded as down while all 7 nodes were up and answering. `accept-new` trusts a first key but still refuses a *changed* one, so a genuinely swapped host reports `KEY` instead of passing silently (which `=no` would do). `run_test.py` and `stop_agents_v2.sh` pass `StrictHostKeyChecking=no` on every hop, so runs themselves were never affected — only the sweep.
- **Clocks: check them before any run whose numbers compare two nodes.** The stock image points chrony at public NTP pools that most sites here cannot reach; on 2026-09-14, 66 of 92 nodes showed `Reach 0` / `LastRx 30d` and were free-running **0.4–1.1 s apart** (two hosts on the same LAN, ~930 ms). Nothing surfaces this on its own — `chronyc tracking` keeps printing the microsecond offset of its last sample, which is a month old. The one reliable indicator is `timedatectl`'s `System clock synchronized`. Repair with `./fix_slice_clocks.sh` (run as root on the database node; `--check` reports and changes nothing), which points every agent at `database` as its time source and steps rather than slews. A rebuilt slice gets the same thing from `notebooks/db_node_setup/07_ntp.sh`, wired into `setup_all.sh`; both read their chrony config from `notebooks/db_node_setup/ntp_conf.sh`. The delegation context age's headline series is immune by design, but `ctx_age_remote_*` and every cross-node latency are biased by the full offset.
- **Level-1 agents default to `resource`** (changed 2026-09-18; the default was `llm`). It is
  still a *separate* key from `--agent-type` and does not follow it, so an all-LLM hierarchy
  needs `--hierarchical-level1-agent-type llm` explicitly — and every host that might get a
  coordinator then needs `OPENAI_API_KEY`, since `LlmAgent.__init__` builds its bidder eagerly.
  Under the old default a coordinator died at startup wherever placement put it on a host
  without the key: two log lines then silence, with the run looking busy until the cap expired.
  Every launcher script in the tree already passed `resource`, so the default was only ever
  reached by accident. Pinned by `tests/test_fleet_sizing.py::TestCoordinatorTypeDefault`.
- `agent_hosts.txt` lists all agent hostnames, one per line. It is **deleted by `cleanup_between_runs`** unless it is the resolved `--agent-hosts-file`, so it will often be absent on the database node and must be regenerated before a remote run.
- Remote-mode tests are launched from this node with `--db-host database`, e.g.:

**Workflow DAGs (2026-09-15).** `pegasus_to_swarm_converter.py --dag-gating` reconstructs a real workflow's dependency graph from the profiles the extractor already produces and emits it as a per-job `data_predicate` — `{"kind": "files", "files": [...]}`. No extra extraction is needed, because a Pegasus DAG's edges *are* file dependencies: job B depends on job A exactly when B lists an input A lists as an output. The agent's existing gate (`_data_predicate_ready`) dispatches on predicate shape and keeps a job out of selection until `Repository.data_available` says those names exist; a job publishes its `data_out` names on completion **and only when `exit_status == 0`**, so a failed parent holds its children rather than releasing them onto inputs that were never written. Only edges *inside* the converted set become predicates — a root's staged-in inputs are never produced by the run, and gating on them would hold the whole DAG at its root. `--dag-gating` forces `--data-nodes per-file`: per-site collapses a job's inputs and silently loses edges (measured on the 11-job earthquake workflow, 10 of 13 survived). `conversion_summary.json` reports `dag.edges` and `dag.roots` — check them, since a partial DAG still runs and looks healthy. The readiness registry is **run-scoped and cleanable**: its key is `data_ready:<SWARM_RUN_ID>:0:names`, which contains a colon so `delete_all("*")` (what `cleanup.py` runs between runs) reaches it, *and* carries the run id so a cell that skipped cleanup still cannot inherit — a bare key meant the next run of the same workflow found every file name present and released the whole DAG on its first tick. **Completion and publication are one write:** `execute_job` passes the produced names to `repository.save(..., produced_data=[...])`, which adds them to the registry inside the same MULTI that records the job COMPLETE. As two writes an agent dying in between gated every descendant of that job for the rest of the run, and no retry queue covers that because the queue dies with the agent; as one transaction there is no in-between, and a job left short of COMPLETE is reselected by the existing machinery. **Persisting is a separate concern from executing**, and `execute_job` no longer shares one `try` for both: a Redis blip on the completion write used to be handled as an execution failure, rewriting a successful job to `exit_status=1`, persisting it COMPLETE so reselection would never revisit it, and publishing nothing — stranding every descendant for the rest of the run. Only a real execution exception may set a non-zero exit status; `_persist_completion` queues a failed write and `_retry_unpersisted_completions` re-writes it on the periodic tick, **outcome and outputs together** (publishing without the completion would release descendants of a job not recorded as done). `_publish_produced` remains the out-of-band route for a caller with no completion write to ride on, and a failure there is queued and retried the same way — the names are what release descendants, so a dropped publish looks exactly like a workflow that is legitimately waiting. Verified against Redis on that workflow: 13/13 edges, one root, and it schedules in three waves of 1, 7 and 3, which is its declared shape. **Jobs still simulate their wall time** — this is ordering, not execution. Real execution additionally needs a subprocess in place of the sleep; the executable/container half of that is now carried (see below). **Both selection loops gate on the predicate since 2026-09-20.** `LlmAgent.selection_main` overrides the whole loop and had no gate, so an LLM-agent run of a DAG-gated workflow ignored the DAG and could schedule a child before its parent wrote the files it reads (code review §11). `_gate_on_data_predicates` is now shared by both, and in the LLM loop it runs before designated bidding so an ungated job spends no inference. Tests: `tests/test_workflow_dag.py`, `tests/test_review_smaller_items.py`.

**Workflow execution: executables and containers (2026-09-16).** Carried, not yet run — the point is an apples-to-apples comparison against the same workflow on Pegasus. `pegasus_profile_extractor.py` now records `executable_db`/`argv_db` (from `invocation`, which had them all along) plus `pfn_db`/`pfn_type_db`/`container_db` from the **transformation catalog**, which is where a container is declared and which the stampede DB does not contain. `load_transformation_catalog` prefers the run dir's planned copy (`catalogs/transformations.yml`) over the workflow-root one — the latter can have been edited since and would then describe a run that never happened — and prefers a non-`local` site, whose pfn is the science code rather than a submit-host wrapper. **Two paths are needed, not one:** `invocation.executable` is the path *inside the container* (`/srv/analyze_moisture`), the catalog's `pfn` is the host path of the code staged there; the pfn says what to ship, the in-container path says what to invoke, and neither alone can re-run the job. `ExecutionSpec`/`ContainerSpec` (`swarm/models/execution.py`) carry them on `Job` and round-trip through Redis beside `QuantumSpec`. All optional: a job with no spec simulates exactly as before, so no existing result moves and corpora converted earlier stay valid rather than becoming half-runnable. **Empty arguments and unknown arguments are different and the difference is enforced** — `[]` is "the command line had none" (most Pegasus jobs pass data by file), `None` is "`argv` could not be parsed", and `ExecutionSpec.runnable()` refuses `None` rather than reading it as `[]`, because running a different command than the one being compared against is the one error this comparison cannot absorb; it survives the converter boundary and the Redis round trip, both pinned by tests. `runnable()` also refuses a container named with no image (the job would fall back to whatever the host has installed, the exact variable a container removes) but allows a missing pfn for an `installed` transformation, already in the image. **Execution is wired** (`runtime.execution.mode: real`, default `simulate` — see below). Drought is *not* available: it exists only as profile rows, with no source, scripts, container or inputs anywhere on the Pegasus host; `soilmoisture` (5 jobs), `airquality`/`species-occurrence` (11), `nextgen` (19), `fedcast` (20), `tnseq` (35) and `meerkat-2mass-mosaic` (59) are complete. **Apptainer 1.5.3 is installed on all 92 agents** (`setup_apptainer.sh`), so a workflow's own `.sif` runs natively and `image_overrides` is not needed for it; the VMs also still have docker. Tests: `tests/test_workflow_execution.py`.

**Real execution (2026-09-16).** `runtime.execution.mode: real` makes `Job.execute()` run the job instead of sleeping; `simulate` (default) is unchanged, so an agent that says nothing about execution behaves exactly as it always has and an unknown value **raises**. Only jobs carrying an `execution` block execute — a synthetic job in a `real` run still simulates, so a workflow and a background load can share one run. Everything lives in `swarm/execution/runner.py`, kept separate from `job.py` so the simulated and real paths cannot drift into one another's error handling. **The real exit status is the process's own and overrides `should_fail`**, which replays what the job did on somebody else's cluster months ago; that precedence is the difference between a comparison and a recording, and it is pinned by a test. **A refusal fails the job and never falls back to the sleep** — a run silently mixing executed and simulated jobs, with nothing in the results telling them apart, is worse than one that stops — and is logged at ERROR, since it is a configuration fault that will repeat for every job. What gets refused: an unresolvable executable (no basename search — two workflows can both have a `process.py`, and running the wrong one succeeds and produces plausible output), unknown arguments, an imageless container, no working directory, no container runtime (never a fallback to the host, which would silently redefine what was measured as "whatever this host has installed"), and **a `.sif` image on a docker-only host** — which is the *default* situation here, so it is refused up front with a message naming `image_overrides` rather than left to fail inside docker. `work_dir` is **shared across the jobs of a run** (the run id is appended): `data_in`/`data_out` are bare logical file names, so job B finds job A's output only if both ran in the same directory, and per-job directories would silently break every DAG edge. `path_rewrites` maps a catalog's submit-host `pfn` onto wherever the code was staged (longest prefix wins, so config order cannot decide which code runs). `runtime.execution.bundle` points at a converted-jobs directory and sets all three roots at once: the converter writes a **self-contained bundle** — job records, the executables in `code/<transformation>/` (one copy per transformation, namespaced because two may ship a `run.py`), the declared replicas in `inputs/`, and `manifest.json` with a sha256 per file, because a path says where code was and not *which* code it was. Images are referenced not copied (gigabytes; `--bundle-images` overrides) with their checksum recorded either way. A partial bundle reports on stdout and in the manifest rather than looking whole and failing per job later. The manifest carries `bundled` (bundle-relative, for auditing) *and* `root_relative` (what goes in the job record) — conflating them put `code/` in the path twice and every job refused. `--no-bundle` restores path-only records; simulated jobs have nothing to bundle and are unaffected. `runtime.execution.roots` (`code`/`inputs`/`images`) is the other half, for jobs authored by hand rather than converted: **an absolute path is used as written, a relative one resolves under its root**, and a relative path with no root is a refusal naming the key rather than a fall back to the process cwd. The three roots map onto fields that already exist — `execution.pfn`, `Job.data_in`, `execution.container.image` — so there is **no new inputs field**: a second list would be a second source of truth for what a job reads. The runner stages `data_in` into the work dir before the job starts, and **never overwrites** (an existing file is a parent's output or another agent's copy; a stale replica over it corrupts a DAG invisibly), copies **atomically** via temp+`os.replace` (the dir is shared and agents stage concurrently; a half-written file is readable and looks complete), and **refuses a missing input** rather than letting a job write empty output that looks like a result. Stageable code is bind-mounted onto the in-container path Pegasus used, reproducing what Pegasus did and keeping `executable_db` meaningful; `installed` code is not bound over. Output goes to files under `<work_dir>/.swarm-logs/` rather than pipes (several jobs run at once and a chatty one would grow unbounded in the agent's own process); a timeout kills the whole **process group** — a container launcher is a parent of the real work, so killing only the child leaves the container running — and then **reaps** it, since killing without waiting leaves a zombie per timeout in a process that runs jobs for its whole life. A **`docker://` scheme is runtime-dependent and is resolved at `build_command`, not `resolve_image`**: docker wants a bare `repo:tag`, apptainer *requires* the scheme and given a bare reference looks for a local file of that name; stripping it early broke apptainer with an error naming a path nobody wrote. The job's environment is the agent's **minus the agent's own secrets** (`job_environment` drops anything matching KEY/TOKEN/SECRET/PASSWORD/CREDENTIAL, plus `SWARM_RUN_ID`/`LLM_BASE_URL`) — a job otherwise inherits `OPENAI_API_KEY` into a container built by someone else whose stdout is captured to a shared filesystem. A denylist, not an allowlist: real workflow code needs ambient environment (PATH, HOME, proxies), and an allowlist would break workflows in ways that look like workflow bugs. Tests: `tests/test_real_execution.py`.

**Data staging (2026-09-21).** `runtime.execution.staging.enabled` (default **false**) moves a workflow's files between agents instead of relying on a shared mount. Off, an input resolves in the working directory or under `roots.inputs` exactly as before, and nothing here listens — every measurement to date is on that path. On, a job's outputs stay on the agent that produced them, a **location registry** says which agent that is, and a consumer elsewhere fetches them. Design and the rejected alternatives: `docs/STAGING_DESIGN.md`. What is worth knowing before using it:

- **Transport is a second gRPC service on a second port, on the same host consensus uses** (`grpc.port + staging.port_offset`, default +1000). Same host is the point: `grpc.host` is what `AgentInfo` advertises and what peers dial, so a transfer traverses the **same measured data-plane paths** as consensus. SSH was rejected despite the root mesh existing (`02_ssh_mesh.sh`), because `ssh agent-N` resolves through `/etc/hosts` to the management path — data would move over a different network than the one E3a bins by RTT, which is the same shape of error as NFS flattening locality. Separate *port* is also the point: a multi-megabyte transfer must never queue behind, or ahead of, the consensus messages whose latency is being measured, and the transport's P0-4 counters keep counting consensus alone.
- **The location registry is a HASH beside the readiness SET**, `data_loc:<run>:0:names` → `{agent_id, host, port, produced_at}`, written **inside the same MULTI** as the completion and the readiness names. Same one-write rule, one step further on: a descendant that can see a name as ready but cannot find out where it is gets released and then refuses to stage, which reads as a staging bug and is really a torn write. The readiness SET is untouched, so `data_available` stays one `smismember` on the scheduling path; a location is read only when a file is actually about to move. No path and no checksum in the record — the server resolves names against its own published map, and the transfer digests the stream and verifies at the receiver, which costs nothing when nothing moves and still catches a truncated transfer.
- **The server serves only names it published in this run**, by map lookup, never a directory join — an unpublished name has no path at all, so there is no traversal surface. A mismatched run id is refused, the same guard the run-scoped registry key gives.
- **`stage_inputs` tries four sources in order, and the order is load-bearing:** the working directory, then **a name produced by this run on another agent**, then `roots.inputs`, then refuse. The produced name deliberately beats the inputs root: workflow file names are a flat namespace (62 colliding names measured in the shipped profile), so a same-named file in the root is a collision, not a copy, and preferring it would feed a child last week's file while looking healthy. A produced file that cannot be fetched is a **refusal naming the producer**, never a fall back to a same-named file elsewhere.
- **A lookup that is missing or fails is a REFUSAL, not a fall back to the inputs root.** The first version warned and resolved locally, reasoning that a brief Redis outage should not fail a job whose input is on disk. That is wrong with staging on and wrong in the way this tree keeps being bitten: the *fallback* path was more permissive than the path it stood in for. A name a parent produced lives on another agent, the lookup is the only thing that knows which, and resolving it from a same-named file in the inputs root is exactly the stale-collision read the source order exists to prevent — reached through the error path instead of the happy one. Refusing is loud and retryable; a stale input is silent and produces plausible numbers. Same for staging enabled with no context installed, which was the silent version of the same hole. **The refusal is per name, not per job**: its first version returned before any input was examined and so rejected jobs that could not read a stale file at all — one with no inputs, and one whose inputs a parent on this agent had already written into the work dir. It now fires only where a name has fallen past the work dir and is about to be read from the root, which is the one place the ambiguity exists. Both the hole and the over-correction were caught by the stop-time review gate.
- **Regenerating the proto raises the gencode floor, and that breaks more than staging.** Adding the transfer service regenerated `consensus_pb2.py` with protobuf 6.31.1, lifting the `ValidateProtobufRuntimeVersion` floor from 5.29.0 — and that module is imported by the consensus transport, so too old a runtime stops **every** agent, staging or not. `requirements.txt` now states `protobuf>=6.31.1` rather than leaving it implied by whoever last ran protoc. Measured on the slice 2026-09-21: agents 7.35.1, database node 7.36.1, and the regenerated module imports cleanly on both. **Re-check that pin after any protoc run.**
- **Containment is at the point the local path is built.** `fetch` refuses a name that is not a plain file name: joined onto the destination, `../../x` writes outside the working directory *before* the server's refusal is ever read, so the server being careful is not enough. Found by its own test.
- **NOT BUILT, and it decides whether a cell is valid** (`STAGING_DESIGN.md` §6): stage-out; transfer accounting in `collect.py`; and **producer durability** — a dead agent's outputs are gone, its job is COMPLETE so nothing re-runs it, its name is in the readiness registry so every descendant is released, and they all then refuse. **Do not enable staging on a failure-injection cell** (E2b, E6 kill agents) until that is decided. With staging on the work dir must be **local** per agent; a shared one makes every fetch a no-op and measures nothing. Tests: `tests/test_staging.py` (29).

**`setup_apptainer.sh` (2026-09-16).** Installs Apptainer on the slice so catalogs' `.sif` images run natively rather than being substituted by a Docker build — a different artefact from the one Pegasus ran, which weakens the comparison. Run as root from the database node; `--check` reports and changes nothing, and **both paths exit non-zero on a partial fleet**. `ppa:apptainer/ppa` is **unreachable from the agents** (measured: `add-apt-repository` fails while plain apt to the Ubuntu archive succeeds), so the `.deb` is fetched once on the database node and pushed over the root SSH mesh — one download instead of 92, and no dependency on 17 sites reaching Launchpad. Take the plain `_amd64.deb`, **not** `-trixie+`, which does not run on jammy. **setuid is deliberately not installed**: these nodes are Ubuntu 22.04 with unprivileged user namespaces available and no AppArmor userns restriction (a 24.04 default), so the unprivileged path works and is the smaller attack surface; `--suid` forces it where a node needs it. Verification **runs a real container** from a busybox probe image pushed with the package, never `apptainer --version` — a binary that cannot start a container is the same healthy-looking failure as a mount that cannot be written to. Note `singularity` on these hosts is a **compatibility symlink to apptainer**, so `container_runtime: auto` prefers `apptainer` explicitly: relying on the alias depends on something a future package could drop and logs a command naming a program that is not what ran.

**`setup_nfs_workflow.sh` — shared filesystem, as scaffolding (2026-09-16).** One export from `database`, mounted at an **identical path** on every agent so a job record's absolute paths resolve wherever it lands. Run it as root from the database node; `--check` reports and changes nothing. **It is not a configuration any published number comes from:** reads come from the export rather than an agent-to-agent transfer, so no data-movement number from such a run describes the system; every agent is equidistant from the data, so the connectivity/DTN penalties price a locality that no longer varies; and it is a WAN mount across 17 sites, so job wall times include transatlantic latency and are not comparable to the Pegasus run being compared against, which used a local filesystem. Real staging replaces it. Container images stay **off** the export (`--stage-image` copies to each agent's local disk) — a 3.1 GB `.sif` pulled over a WAN mount per job start would dominate every measurement taken. Three traps, all measured on the slice: `dpkg -l <pkg>` exits 0 for a package apt merely *knows about*, so it is not an installed-check and using it as one skips the install; a **root-owned sticky export silently breaks squashed writes** — the client can create a file, so `touch` and `findmnt` both look healthy, but writing content fails with EACCES (`root:root 1777` FAIL, `nobody 1777` OK, `root:root 0777` OK), so the export is chowned to the squashed user and keeps its sticky bit rather than dropping to 0777 and letting jobs delete each other's outputs; and consequently the mount is verified by a **real write the server reads back**, never by `findmnt`. Both the setup path and `--check` **exit non-zero on a partial fleet** so a campaign script can gate on them — a partial setup that reports success stays invisible until a job lands on a host nobody remembers skipping.

**Quantum/hybrid jobs** (see `docs/QUANTUM_HYBRID_DESIGN.md`): `generate_configs.py --quantum-agents-pct 0.25` gives a subset of agents a `quantum_backend`; `job_generator.py --quantum-fraction 0.2 --hybrid-fraction 0.1` emits jobs with a quantum component (one-shot offload or variational classical<->quantum loop). `run_test.py` accepts the same three flags and forwards them. Models in `swarm/models/quantum.py` (`QuantumSpec`/`QuantumBackend`); `Capacities.qubits` carries the allocatable qubit count; feasibility/cost wiring in `resource_agent.py` (`_quantum_feasible`, `qpu` cost weight — default 0.0, classical runs unchanged).

**Phase 2 — data-triggered split scheduling** (`--split-hybrid` on run_test/job_distributor): hybrid jobs decompose into a quantum sub-job (`<id>-q`, measurement producer) and a classical sub-job (`<id>-c`, stream consumer) placed on different agents. `swarm/quantum/measurement_layer.py` = Redis-streams measurement layer; `swarm/quantum/split.py` = split/post-process builders + `split_comm_penalty`. ## Architecture

### Five-Layer Design

1. **Agent Layer** (`swarm/agents/`) — `ResourceAgent` (rule-based), `LLMAgent` (LLM-enhanced), `ColmenaAgent` (Colmena workflow integration). Base class in `agent_grpc.py`.
2. **Consensus Layer** (`swarm/consensus/engine.py`) — Framework-agnostic PBFT-like protocol. Flow: `propose()` → `on_proposal()` (dominance check) → `on_prepare()` → `on_commit()` → quorum triggers `select_job()`. Quorum = `ceil((n+1)/2)`, dynamic based on live agents. An alternative Snow/Avalanche-style engine (`swarm/consensus/gossip_engine.py`, `GossipConsensusEngine`) is drop-in compatible and selected via `consensus.protocol: snow`; it replaces the 3-phase broadcast with k-peer sampling and finalizes exactly-once via Redis `SET NX` (`repository.try_claim_assignment`). **Exactly-once is a Snow property and only Snow's** (code review §10): `try_claim_assignment` has exactly one caller, the Snow engine, and PBFT's `select_job` persists the job READY claiming nothing. `calculate_quorum` is a majority of `live_agent_count` — each agent's *own* `neighbor_map` — floored at 1, so under a partition every side reaches its own quorum (20 agents split in two: 10 live, quorum 6, each side alone) and a fully isolated agent has quorum 1. **Both sides of a partition finalize the same job under PBFT and nothing prevents it.** Never write the safety argument protocol-neutrally, and never read a claim-key audit as a PBFT result: PBFT writes no claim keys, so such an audit returns 0 there by construction — absent, not zero.
3. **Selection Layer** (`swarm/selection/engine.py`) — Cost matrix computation with LRU caching. `penalties.py` provides live (non-cached) penalty helpers. An agent proposes for a job only when it computes **itself** as the minimum-cost assignee; there is no relative threshold around that (see the `selection_threshold_pct` note below).
4. **Communication Layer** (`swarm/comm/`) — gRPC server/client/transport defined in `consensus.proto`.
5. **Data Layer** (`swarm/database/repository.py`) — Redis persistence for jobs, agents, and consensus state with secondary indices by job state.

### Key Integration Pattern

Consensus and selection engines are **decoupled** from agents via adapter classes (`_HostAdapter`, `_TransportAdapter`, `_RouteAdapter`) in `resource_agent.py`. Engines remain framework-agnostic; agents handle all side effects. When modifying consensus logic, changes to `ConsensusEngine` must stay framework-agnostic — side effects belong in adapters.

### Supporting Modules

- `swarm/topology/topology.py` — Ring, Mesh, Star, Hierarchical topologies with neighbor/routing logic
- `swarm/models/` — `job.py`, `capacities.py`, `agent_info.py`, `data_node.py`, `role.py`
- `swarm/rl/` — Multi-Armed Bandit (Epsilon-Greedy, UCB1) for hierarchical delegation
- `swarm/queue/` — Job queue implementations

- `swarm/consensus/gossip_engine.py` — Snow/Avalanche consensus engine (Phase 3). See `docs/GOSSIP_CONSENSUS_DESIGN.md`

Code fallback when absent is `heartbeat`. **SWIM is advisory and must stay that way (2026-09-20).** It used to gate `broadcast` as well: a peer in SWIM's FAILED set received no consensus traffic, while `calculate_quorum` went on counting `neighbor_map`, which still contained it — so a false positive removed a voter without lowering the bar it had to clear, and SWIM false-fails *precisely* under consensus bursts (acks queue behind the single inbound consumer and blow the probe window, which is why `live_peer_ids` already reads an empty SWIM live set as a false one). Second half of the same defect: `_merge_one` ordered claims by severity alone, so the ALIVE-at-incarnation+1 that `_maybe_refute` emits was rejected everywhere and **a FAILED verdict was permanent** — no peer probes a FAILED member again, so a false positive cost that peer its place in Snow's sample and the gossip fan-out for the whole run. `_supersedes` now takes incarnation first (only the subject raises its own, so a higher one is first-hand word) and severity only within one incarnation, dropping a stale rumour however severe. `tests/test_swim_advisory.py`

- `instrumentation.decision_log_max` / `textfile_dir` / `textfile_period_s` — Run instrumentation (P0-4). Everything lives in `swarm/utils/instrumentation.py` so `metrics.json` and the Prometheus export render from the same dicts. On by default except the export, which needs `textfile_dir` (a node_exporter textfile-collector path on the agent host; `--textfile-dir` on `generate_configs.py`/`run_test.py` sets it, so a Grafana-instrumented campaign is not chosen by a hand edit). What is recorded, per agent: consensus **message counts and protocol bytes** by direction and type (counted in `GrpcTransport`, the one funnel every message crosses exactly once — a shed fan-out send counts as `dropped`, never as `sent`); **finalization** via `engine.consensus_stats()` on both engines (Snow: rounds/queries/elapsed, `abandoned`, which only means anything read next to `finalized`, and `finalize_lost` — a decision whose Redis CAS won but whose object could not be read, so no leader was elected and no participant committed: it produced no assignment, is deliberately **not** counted in `finalized` and stays out of the latency distributions, and a non-zero value means work was lost. PBFT: votes and elapsed at the **proposer** only, no `rounds_*` because a column of 3s invites a meaningless cross-protocol comparison, and a re-proposal restarts the clock so a 60 s reselection timeout stays out of a sub-second distribution. PBFT reports **neither** `abandoned` nor `finalize_lost`: it does not abandon (a stuck object goes to the reselection timeout) and has no CAS, and a hard-coded 0 beside Snow's measured count compared a measurement against a placeholder. `collect.py` emits those two columns only when some agent reported them, so a measured 0 still reads 0 and a PBFT cell reads absent); **LLM tokens/latency/failures** per call site, with failures timed, not free; and **delegation decisions**. `decision_log_max` bounds the per-decision rows as a ring — when it binds the *oldest* go, because the converged regime is the one the figures are about — while the aggregates stay exact either way

**Context age at decision time** is the metric that did not previously exist in any form, and the conference paper's only interaction claim (F6) cannot be produced without it. It is measured on **two clocks**, because the obvious single-clock version does not survive a real fleet:

- **Headline (`ctx_age_*`)** — `decision - received_at`, both terms from the coordinator's own **monotonic** clock (`received_at` is stamped in `_note_agent_seen` when a *fresher* child record arrives; re-reading an unchanged record must not refresh it, or a peer that went silent would report age zero until eviction). Immune to inter-host offset *and* to the local wall clock being stepped. Both halves are load-bearing and both were learned the hard way: measured on the slice 2026-09-14, **66 of 92 hosts had not reached an NTP server in 30 days** and were free-running 0.4–1.1 s apart (two hosts on one LAN disagreed by ~930 ms), which drove one coordinator's entire age column to zero; and the repair configures the fleet to *step* at 0.1 s of drift, so a wall-clock pair spanning a correction is wrong by the step. One host is not enough — it has to be one host's monotonic clock. The stamps are a side map on the agent, never an `AgentInfo` field: that object round-trips through Redis, and a monotonic value is meaningless off its host.
- **End-to-end (`ctx_age_remote_*`)** — `decision - observed_at`, using the child's wall-clock `last_updated`. The more complete quantity (it includes propagation), but it straddles two machines and needs a synchronised fleet. A negative value there is clock offset, clamped to 0 and counted in `ctx_skewed_ages`, with the worst magnitude in `ctx_skew_max_s`. Those two are **validity** columns, not results — a count alone cannot separate a 1 ms artefact from a 1.1 s free-running clock. Check them before reporting anything from the remote series.

`GroupSnapshot` carries the newest *and* oldest stamp of each pair, because a group of nine where one child went quiet is genuinely fresh on one and stale on the other. The age is taken at the **decision**, not when the view was built: under `delegation.policy: llm` those are seconds apart, and `decide_s` is stored alongside so the age at build is `age - decide_s`. Two more things that would have made the column quietly wrong and are pinned by tests: an unknown age (no live child, or `AgentInfo.last_updated` still at its 0.0 default) is counted in `ctx_unknown_groups` and never substituted with a large one — the naive reading is a 56-year age landing in the p99 exactly where the dead groups are; and the new `GroupSnapshot` fields are provably invisible to `ContextExtractor`, since a changed `schema_version` discards every persisted LinUCB model. The record is written by `_delegate_child_groups`, a wrapper *around* `_select_child_groups` rather than inside it, because `LlmAgent` re-enters the bandit on five fallback routes — so there is exactly one record per delegation and it names the rule that actually decided (`llm`, `bandit`, `bandit_all`/`all` for a fan-out covering every candidate, `random`). Exported to `metrics.json` as `instrumentation` + `delegation_decisions`, summarised on the `[STATS]` line, and collected by `evaluation/collect.py` into per-run summary columns (fleet **sums**, not per-agent means, whose denominator would vary with metrics completeness) plus `decisions.csv` — one row per decision, which is what F6 plots and what the oracle (P1-1) labels offline

**Delegation regret (P1-1)** — `evaluation/oracle.py` scores each delegation against the best candidate group available, using the injected failure profile as ground truth and the agents' own `_select_failure_phase`/`_resolve_failure_rate` to resolve it (one definition; a second copy would drift and make every regret number quietly wrong). `collect.py` puts `regret_total`, `routing_accuracy` and `regret_ctx_age_corr` on the wide row next to the context age, so F6 comes from a single collector run. Everything it cannot know, it refuses rather than approximates — each of these was a real bug that produced a flattering number: the profile must be archived in `run_meta.json` (`ground_truth`), since the base config is edited between arms; failure phases resolve on each **member agent's own** `failure_sim_start`, never the coordinator's or the run's, and there is no fallback clock; a decision is scored only if **every** candidate can be priced, because pricing a subset and taking the best of it records a bad choice as optimal when the genuinely best group dropped out; and a decision whose candidates are all equally good is not graded. Run `--validate` on the first run of any cell whose figure is regret: it compares the profile's predictions against real exit statuses, gated on job-weighted error and on per-type deviations beyond 2 SE (the raw worst per-type error trips on a six-job type in almost every run). That SE is the **Poisson-binomial** one over the individual predicted rates, not the binomial at their mean — the trials are not identically distributed, and the mean-p form overstates the variance and accepts outcomes the profile makes impossible. **Design the failure profile with contrast *within* each coordinator's candidate set** — a coordinator only chooses among its own groups, so a profile that varies between coordinators makes every choice equivalent and reports a meaningless `routing_accuracy` of 1.0.

**Designated bidding (P0-8)** — `job_selection.designate_bidder` (off by default) has every agent locally compute the same analytic designation and bid only on jobs designated to itself, cutting bidders-per-job from ~3.7 to ~1 so an added agent is a new server rather than a redundant bidder. A per-job deadline (`designate_bidder_fallback_s`, 30 s) keeps it live. **Whether it is working is measured, not assumed**: agents report the distinct jobs they paid an LLM bid for, and `collect.py` reports `bidders_per_job` with `designate_forced_share` beside it. Read the second one first — if the deadline is firing on most jobs, every agent bids anyway, bidders-per-job returns to its undesignated value, and nothing else in the run looks different. Counting rules that matter, all of them mistakes made and caught here: counters are **distinct jobs**, never per loop pass (`gets()` is a non-destructive peek, so an unplaced job reappears ~2×/s and `deferred` inflates ~60×); the share's denominator is the **union** of `mine` and `forced`, not their sum, because a job that loses consensus returns to PENDING and can take both routes; and the retry cost lives in `bid_calls` − `bid_jobs` rather than in the job counts. Note `_designate_bidders` runs only in `LlmAgent.selection_main`, and only 30 of the slice's 92 hosts carry `OPENAI_API_KEY`, so an LLM run must be placed on those (site-clustered, which invalidates any latency or consensus number from it).

## Development Guidelines

**Adding new agent types:**
1. Inherit from `Agent` base class in `swarm/agents/agent_grpc.py`
2. Integrate consensus engine via adapter pattern (see `ResourceAgent` in `resource_agent.py`)
3. Implement `compute_job_cost` and `is_job_feasible` methods

**Tuning selection behavior:**
- Adjust cost weights in `config_swarm_multi.yml` first before changing code
- Consider live penalty functions in `swarm/selection/penalties.py`

**PBFT stragglers (2026-09-18, `tests/test_pbft_stragglers.py`).** Every tier wider than its quorum produces `n − q` late PREPAREs and COMMITs per job. Finalization used to erase all memory of the decision (`_forget_object`) and nothing marked the job decided locally (`select_job` persists READY; the dedupe set is fed by `schedule_job` ~0.5 s later at a leaf and at a coordinator not until the delegation monitor marks COMPLETE), so each straggler re-adopted the proposal **with the sender's wire vote lists**: a second COMMIT broadcast per late PREPARE, a second finalization per late COMMIT — the 2026-09-15 COMMIT fix undone by its own cleanup, biasing messages/finalize counts against PBFT in the collapse cell. Now `ConsensusEngine._finalized` remembers `(object, p_id)` after the containers clear (bounded; `forget_decision` when the host returns a job to PENDING), `ResourceAgent._decided_jobs` makes `is_agreement_achieved` true at finalize (built in `_init_decision_state`, which doubles must call; the periodic pending scan forgets a decision only when the fetched record's `last_transition_at` postdates it — evidence of a reset, never elapsed time), and participants record the *proposer* as leader rather than the last COMMIT's sender. **No E5/F2 number measured before this is citable.**

**Review-pass fixes (2026-09-15), all pinned by `tests/test_review_fixes.py`:** PBFT sends **one COMMIT per proposal** — the old guard asked `incoming.contains(...)`, false for the proposer's own proposal, so a proposer re-broadcast on every PREPARE past quorum and inflated messages-per-job against PBFT; it is now keyed on a `_commits_sent` set of `(object_id, p_id)` released with the object, so adopting a better proposal and re-proposing after a reselection timeout both still commit. Snow's `finalized_count`/`abandoned_count`/`sends_dropped` are incremented under a dedicated `_stats_lock` (separate from `_lock`, so it is never held across a host callback), and a finalize whose CAS or callback raises is counted in a new `finalize_errors` — `finalized + abandoned + finalize_errors` is the whole population, and a non-zero third term means assignments were lost. An unknown `consensus.protocol` or `consensus.hybrid.{level0,coordinator}` name now **raises instead of silently becoming PBFT**. SWIM's `_indirect_acked` is released once an ack is forwarded or orphaned, instead of growing for the life of the agent. `batch_tests_v2.py` sizes auto-generated hosts with `math.ceil` (it floored, so 270 agents at 4/VM asked for 67 hosts and needed 68) and forwards `--expect-silent-agents`. **Both gaps that pass left open are now closed** (`docs/FGCS_EVAL_PLAN.md` Appendix A.11): failed-agent reassignment searching only the local pending queue was a defect and is fixed (see *Failed-agent job recovery* below), and the `# TEMP HACK` building the level>0 cost matrix over `[self]` only was a design decision, now named as `job_selection.coordinator_cost_matrix` and **measured** rather than hidden — the default behaviour is unchanged. Tests: `tests/test_coordinator_matrix.py`.

**Debugging consensus (PBFT):**
1. Set `log-level: DEBUG` in config
2. Check `engine.outgoing`/`engine.incoming` proposal containers and `engine.conflicts`
3. Verify quorum via `calculate_quorum()`
4. Check `save_consensus_votes()` output in Redis

**Debugging consensus (Snow, `consensus.protocol: snow`):**
1. Confirm the engine started: grep logs for `[snow] consensus engine started`; look for `[SNOW_LEADER]`/`[SNOW_PART]` finalization lines
2. `engine.conflicts[job_id]` counts rounds that failed the α-threshold; persistent growth means no candidate is dominating. Bounded at 4096 objects since 2026-09-20, evicting oldest first, matching PBFT — it was unbounded on the engine that runs by default (code review §11)
3. Exactly-once is enforced by `repository.try_claim_assignment` (Redis `SET NX`) — inspect assignment keys with `dump_db.py` to confirm no double-assignment. This check is **meaningless under PBFT**, which writes no such keys: an empty result there means the audit does not apply, not that nothing was double-assigned
4. Tune `consensus.snow.{k,alpha,beta}`; enable `gossip` and `failure_detection: swim` so peer cost estimates and the live-peer sample stay fresh

**Failed-agent job recovery (2026-09-15).** `_reassign_jobs_from_failed_agent` sources its candidates from **Redis, not the local queues**: a job that won consensus is no longer in any peer's pending queue (`_update_ready_jobs` removes it), so the old version looked there, found nothing, logged "likely completed" and dropped it — and since its persisted state is READY or RUNNING rather than PENDING, no agent re-added it and `_restart_selection` (which only covers the three consensus states) never saw it. The work was silently stranded for the rest of the run, and **P0-9 widened that window from milliseconds to the job's whole duration** (a scheduled job used to flip to COMPLETE at once, so a dead agent's job merely looked finished). The job record's `leader_id` is the authority on who held it. Three things had to land together: **release the exactly-once claim** (`repository.release_assignment`) — `try_claim_assignment` is a `SET NX` that nothing ever deleted, so a re-finalization kept returning the dead agent and reassignment could not work under Snow at all; **one reassigner per (job, failure)** via `repository.try_claim_reassignment` (a `SET NX` with a TTL, so a reassigner that itself dies does not strand the job) — every live agent detects the same failure at the same moment, and a second reset landing after the first reassignment has won a fresh election would clobber a live assignment and run the job twice; and **peers must forget it**, so `_update_pending_jobs` now discards a job from `completed_jobs_set` when Redis says it is PENDING again, or `is_agreement_achieved` stays true and every commit for the reassigned job is skipped. E2b and E6 measure exactly this path. Tests: `tests/test_failed_agent_reassignment.py` (11; 9 fail against the pre-fix tree).

**Agent logs:** `<run-dir>/agent-<id>.log`. Dynamic agent logs: `local_agents_initial_start.log`, `local_agents_dynamic_start.log`

**Run identity and metrics completeness (every run):** `run_test.py` mints a `run_id`, exports it as `SWARM_RUN_ID` (inherited locally, re-exported over ssh for remote agents), and records it in `<run-dir>/run_meta.json`. Agents stamp it on the `metrics:<id>` payload they write to Redis, and the plotting step is passed `--metrics-run-id` so a payload from another run is dropped with a warning instead of being read as this run's — an agent that outlives its run writes its metrics whenever it is finally killed, which can be after the next run has flushed Redis. After stopping the agents the runner waits (`--metrics-wait-seconds`, 120s) for every launched agent id to report, then **exits 3** if any are missing and writes `<run-dir>/metrics_shortfall.json`; `evaluation/collect.py` carries that as `metrics_complete` / `agents_missing_metrics` columns. A failure-injection run that SIGKILLs agents must declare it — `--expect-silent-agents 3,7` (preferred: it also checks *which* agents were silent, so a kill that hit the wrong agent still fails the run, and it warns when the intended kills did not take) or `--allow-missing-metrics N` when the ids are only known after launch, as in `run_hier110_resilience_tests.sh`. A SIGTERM'd agent still flushes and does not need declaring. **Known limitation, dynamic mode:** `swarm-multi-start.sh` pkills every `main.py` on a host before launching, so dynamic agents that wrap onto an occupied host kill the agent already there; its early metrics carry this run's `run_id`, so the completeness gate passes for a fleet that never existed. Give dynamic agents their own hosts until that is fixed. `stop_agents_v2.sh` now waits for each agent process to actually exit (`--drain-timeout`, 45s) before SIGKILL, fans out across hosts in parallel, and exits non-zero if any host could not confirm; `run_test.py` also reaps leftovers **before** flushing Redis at startup.
