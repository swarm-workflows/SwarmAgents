# Snow/Gossip Follow-up Paper — Evaluation Plan

**Goal:** A follow-up paper to `SWARM_Escience26_Consensus` (eScience'26, PBFT-based
SWARM+) demonstrating that the **gossip/Snow consensus stack** removes PBFT's scaling
and latency walls while preserving exactly-once assignment.

**Common yardstick:** Pegasus weak-scaling workloads (~18–20 jobs/agent), reusing the
canonical 2188-job Pegasus trace set at the 110-agent point.

---

## Motivation from the eScience paper (our baseline)

The eScience paper is **PBFT-only**; its own results supply the motivation, and its
conclusion explicitly names *"gossip-based consensus to mitigate the latency sensitivity"*
as future work.

| PBFT wall (from the paper) | Evidence in paper | Snow/gossip claim to test |
|---|---|---|
| Flat O(n²) livelock | Mesh-90 ≈51% completion; **Mesh-110 complete livelock** (exceeds 60 s reselection timeout) | Flat Snow (k-sampling, O(k) msgs) survives past 30 agents |
| Hierarchical coordinator O(g²) | Hier-250 selection jumps to **24.5 s** (25 L1 coordinators in one PBFT group) | Gossip/Snow at the coordinator tier removes the g² term |
| WAN-latency compounding | netem: added latency (not loss) triggers reselection timeouts | Asynchronous Snow rounds degrade gracefully under latency |

**Weak-scaling anchor (paper Table `tab:pegasus-weak-scaling`):** Hier-30 = 547 jobs,
Hier-60 = 1094, Hier-110 = 2188; all 100% completion, ~1.0–1.09 s selection,
throughput 0.82 → 1.64 j/s.

## Workload data (Pegasus jobs) — reuse the exact eScience set

**Base set = 547 Pegasus jobs**, in
`swarmplus-evaluation-data/runs/pegasus-workloads/jobs/` (547 `job_*.json` +
`conversion_summary.json`). Derived from 547 profiles / 6 production runs
(`pegasus-profiles/pegasus/profiles/all_runs_jobs_profile.json`) via
`pegasus_to_swarm_converter.py`, spanning air-quality, GWAS, metagenome, protein-structure,
RNA-seq, and sea-ice workflows.

**Larger counts are generated by duplication of the 547-job base**, not new traces —
this is how the paper's 1094 and 2188 sets were produced:

```bash
# From SwarmAgents/ — cycles source jobs with new sequential IDs, preserving attributes
python3 duplicate_jobs.py jobs/ jobs_1094/ 1094   # 2×547  (Hier-60)
python3 duplicate_jobs.py jobs/ jobs_2188/ 2188   # 4×547  (Hier-110)
```

For the extended ladder, generate the same way:
`jobs_5000/` (250 agents), `jobs_10000/` (500), `jobs_19800/` (990).

**How the runs were driven** (see `run_pegasus_scalability.sh` in the pegasus-workloads dir):
runs from `/root/SwarmAgents` on the `database` node in **remote mode**, swapping the active
`jobs/` dir by copying `jobs_<N>/` in, then `batch_tests_v2.py --runs 10 --mode remote
--db-host database --fit-all ...`. (Note: that script used `--agents 60/120` at 2/4 agents
per VM for 1094/2188; the paper reports Hier-60/Hier-110 — reconcile agent counts when
reproducing.)

## Experiments

Config toggles only (no new code) for the flat comparisons:
`consensus.protocol: pbft|snow`, `failure_detection.protocol: heartbeat|swim`,
`gossip.enabled`, plus `consensus.snow.{k,alpha,beta}`.

- **E1 — Flat head-to-head (headline figure).** Same **Mesh** topology, swap engine only:
  `Mesh+PBFT` vs `Mesh+Snow(+gossip+SWIM)` across 10→110(→250). Cleanest apples-to-apples;
  answers "does Snow remove the ~30-agent livelock wall?" Metrics: completion, selection
  time, P95, throughput, consensus conflicts / rounds-to-converge.
- **E2 — Weak scaling to WAN scale.** Snow (flat, and/or all-Snow hierarchical) at
  250/500/990, jobs ∝ agents. Compare vs paper's Hier-PBFT points (Hier-250 = 24.5 s,
  Hier-990 = 46 s). Can gossip/Snow match/beat hierarchical PBFT without the coordinator
  O(g²) penalty? **Blocked on hybrid mode if mixed PBFT/Snow is wanted — see caveat.**
- **E3 — Latency sensitivity (netem) — strongest single result.** Reproduce paper's netem
  setup (Hier-110, 2188 Pegasus jobs, 30 VMs), sweep engine × impairment:
  PBFT vs Snow under {+10, +50, +100 ms per-hop; 1%, 2% loss}. Payoff claim.
- **E4 — Failure detection + membership (SWIM).** Reproduce the two resilience scenarios
  (distributed failures; correlated site outage) at 110 agents:
  `PBFT+heartbeat(300 s expiry)` vs `Snow+SWIM(8 s suspect)`. Metrics: detection latency,
  completion under churn, reselection multiplier (paper reports 2.0–2.3× job-log entries).
- **E5 — Message complexity + state freshness.** Instrument message counts and Redis read
  load with `gossip.enabled` on/off across the ladder → substantiate O(n²) → O(fanout).
  Plus selection quality (Jain's) using gossiped state vs Redis ground truth.
- **E6 — Exactly-once safety stress (correctness).** 110+ agents, high submission rate,
  verify **zero double-assignments** via Redis `SET NX` claim keys
  (`repository.try_claim_assignment`).

**Stats protocol (match paper):** 5–50 repeats per config, two-tailed T-test (α=0.05) +
Cohen's d.

## Caveat — hybrid mode not implemented

**Phase 4 (PBFT-in-group + Snow-across-group) is not implemented.** `ResourceAgent`
selects one engine globally, so today you can run *all-Snow* or *all-PBFT* in a hierarchy,
but not the mixed mode the design doc describes (`docs/GOSSIP_CONSENSUS_DESIGN.md`).

Sequencing options:
- **Fast paper:** lead with **E1/E3/E4 flat comparisons** (zero new code; E1+E3 alone are a
  compelling story).
- **Hybrid result in E2:** requires per-level engine instantiation in `ResourceAgent` first.

## Experimental results (2026-07-01, 4-site FABRIC testbed: MAX/RUTG/PSC/CLEM)

Raw data: `swarmplus-evaluation-data/runs/pegasus-workloads/snow-gossip/`. PBFT baseline reused
from `hierarchical-30/60/110`.

**Hierarchical weak-scaling (Snow vs published PBFT), level-0 selection time:**

| Config | PBFT baseline | Snow default (k20/β20) | Snow tuned (k8/β4/200ms) | Completion |
|---|---|---|---|---|
| Hier-30 | 0.96 s | 9.27 ± 1.93 s (5 runs) | 9.37 s (1 run) | 100% all |
| Hier-60 | ~1.01 s | 6.49 s (1 run) | — | 100% |

**Findings:**
- Snow runs correctly end-to-end on the multi-site testbed: 100% completion, exactly-once via Redis CAS.
- Snow is ~9× slower than PBFT on hierarchical ≤10-agent groups (PBFT's best case). **Parameter
  tuning (β 20→4, k 20→8, timeout 500→200ms) did NOT change it** — params were verified applied to
  the generated per-agent configs. So the overhead is **structural** (Snow driver / selection path /
  per-round WAN cost), not the confidence-round count. Needs profiling. Consistent with the paper's
  own "PBFT for <50 agents" guidance.
- **Scaling the hierarchy does NOT help Snow** — groups stay ≤10 agents at every level. Snow's benefit
  needs *large flat* consensus groups, not deeper hierarchy.

**Flat Mesh-120 head-to-head (2188 jobs, 4 sites, 120 agents = 40 hosts × 3, default Snow k20/β20):**

| Engine | run01 completion | run02 completion | level-0 selection |
|---|---|---|---|
| **Snow** | 2188/2188 = **100%** | 1662/1662 processed = 100% | ~57 s |
| **PBFT** | 0/2188 = **0%** | 14/2188 = 0.6% | 175 s (only the 14) |

**THE headline result:** PBFT flat mesh **livelocks** at 120 agents (run01 assigned zero jobs) —
reproduces the paper's Mesh-110 livelock under our multi-site conditions. **Snow stays live and
completes ~100%.** This is a **liveness/completion** win, NOT latency: Snow's per-job selection is
~57s at this flat scale (k-sampling over 120 WAN peers × β=20 rounds) and is throughput-limited
(run02 finished 1662 of 2188 within the 900s cap). Takeaway: **Snow trades latency for
scalability/liveness in the regime where flat PBFT collapses.** Data:
`swarmplus-evaluation-data/runs/pegasus-workloads/snow-gossip/demo-mesh120-{snow,pbft}`.

Note (host arithmetic): use agent counts divisible by agents-per-host — `run_test` floors
hosts = agents//per_host, so 110/3 → 36 hosts and fails ("Not enough hosts"). 120/3 = 40 hosts works.
