# E2 preparation (2026-10-20, revision c125ed8c)

Three inputs E2 needs, built and checked. None of them changes code, and nothing here is a result.

## 1. Failure profile (`campaigns/make_e2_profile.py`)

Hier-90 G=3 has three coordinators (88, 89, 90), each leading three groups. A coordinator chooses
only among its own groups, so each coordinator gets one group of each kind:

| Role | Fails | Groups (coordinator) |
|---|---|---|
| ram-weak | ram_bound jobs at 0.8, all else at 0.05 | 0 (88), 5 (89), 7 (90) |
| cpu-weak | cpu_bound jobs at 0.8, all else at 0.05 | 1 (88), 3 (89), 8 (90) |
| mediocre | every job at 0.3 | 2 (88), 4 (89), 6 (90) |

On the replay-golden mix (64 % ram_bound, 34 % cpu_bound, under 1 % disk_bound), every coordinator
has an oracle failure rate of 5 % and a best context-blind failure rate of 30 %, checked with
the agent's own `_resolve_failure_rate`. `--flip-after-s S` adds E2a's phase, which swaps ram-weak and
cpu-weak after S seconds of each agent's failure clock. The best group per job type then swaps for
every coordinator.

**Validated on the slice.** One run (`campaigns/pilot-e2val.yml`: PBFT, LinUCB shared, Hier-90 G=3,
Poisson 3 jobs/s, `campaigns/config_e2_pbft_linucb_shared.yml`; `runs/pilot-e2val-c125ed8c`). The run was
clean: 1,800 executed, 0 twice, 0 restarts. `oracle.py --validate` (`oracle_validate_e2val.txt`):

| Check | Value |
|---|---|
| Validated | **true** |
| Jobs compared | 1,800 |
| Mean / max absolute error, predicted vs observed failure rate per job type | 0.013 / 0.20 (the max is on a 4-job type) |
| Job types beyond 2 SE of sampling noise | none |
| Decisions scored / with a choice | 1,800 / 1,800 |
| Routing accuracy, regret mean (this one LinUCB run) | 0.626, 0.212 |

**One thing to decide before E2.** The LinUCB cells keep `mab.load_slack: 9`, which narrows each
choice to groups within 9 in-flight jobs of the least-loaded one. It was set to stop herding in E1′,
where no failures were injected. In E2 it can stop a policy from routing by the profile, because the
right group for a job type gets loaded first. That would cap routing accuracy for every arm alike.
In this run the guard narrowed **560 of 1,800** choices (31 %), counted by `load_guard_narrowed`
and `load_guard_decisions` in `mab_stats`. Options: keep it and report it as part of the policy, or run E2 with
it off and report herding beside regret.

## 2. Work-day schedule (`campaigns/make_e2c_workloads.py schedule`, `campaigns/e2c_workday.json`)

A stylized compressed work day, 30 minutes of arrivals in eight segments: overnight 0.3×, a ramp to
0.9×, a morning peak at 1.2×, a lunch dip at 0.6×, an afternoon peak at 1.15×, a decline. Rates are
multiples of 6.5 jobs/s, the E2 topology's drain rate at c125ed8c (PBFT 7.2–7.3, Snow 6.1–6.6,
Hybrid 6.5 jobs/s under the burst). The plan's 4.2 jobs/s came from the old cost model. The peak is
7.8 jobs/s and the schedule needs about 7,900 jobs, so `/root/workloads/jobs_8000` was built with
`duplicate_jobs.py`. **The shape is not from a trace.** No Pegasus or FABRIC submission timestamps were
at hand. Say so beside any E2c number, or replace `SHAPE` with a measured profile.

## 3. Job-mix shift (`campaigns/make_e2c_workloads.py mixshift`, `/root/workloads/jobs_mixshift_1800`)

The same 1,800 jobs, reordered: jobs 1–900 are all ram_bound, and jobs 901–1,800 are 70 % cpu_bound.
Jobs arrive in job-number order. Under the E2 profile the best group for most jobs moves from each
coordinator's cpu-weak group to its ram-weak group at job 901. `mixshift_summary.json` sits beside the
jobs.

## 4. Group outage for E2b (`group_outage.py`, `campaigns/e2b-rehearsal.yml`)

The tool is a campaign `companion:` modelled on `partition.py`. It waits for the run to start
distributing jobs, then SIGKILLs every level-0 agent of one group. It verifies each process is gone,
holds for `--duration`, then restarts each agent the way the run started it (same config, same
`SWARM_RUN_ID` from `run_meta.json`) and verifies each is up. It writes `outage.json` with members,
hosts, `killed_at`, `rejoined_at` and `held_s`. If stopped early it never restarts anyone. Exit 0
only for a complete outage and rejoin; 1 for a kill or restart that did not take; 2 if the run never
started; 3 for a short hold, no rejoin or no run id. `--no-rejoin` leaves the group down and lists
the ids to declare with `--expect-silent-agents`. Tests: `tests/test_group_outage.py` (11).

**First rehearsal: its restart checks are invalid.** The tool's process pattern matched the remote
shell running its own restart script, which names `main.py <id>` literally, so the "already
running" guard and the post-launch UP check both passed whatever the agent did. The pattern is now
anchored on the interpreter (`tests/test_group_outage.py`), and the tool restarts only members whose
kill was verified. The first rehearsal's table is kept for the record:

**Rehearsal 1** (`runs/pilot-e2b-rehearsal-c125ed8c`: PBFT, LinUCB shared, Hier-90 G=3,
3 jobs/s, the E2 profile). Group 4 (agents 41–50, coordinator 89's mediocre group) was killed 120 s
after distribution started and held for 180 s:

| Check | Result |
|---|---|
| Kill / rejoin verified | all 10 GONE / all 10 UP, held 180.0 s, outcome `ok` |
| Run | `ok`, drained, metrics complete (the restarted agents report), 1,800 / 1,800 completed |
| Executed twice | 0 (lower bound: the killed agents' first-life executions are lost, 1,798 of 1,800 recorded) |
| Coordinator 89's delegations to group 4 | 2 of 26 before, **0 of 50 while down**, 22 of 95 after |
| First delegation to group 4 after rejoin (F5) | **51.6 s** (`readopt.py`) |

**Rehearsal 2, with the fixed tool** (`campaigns/e2b-rehearsal2.yml`,
`runs/pilot-e2b-rehearsal2-c125ed8c`; same cell, same group 4, same timing). This is the one to cite.

| Check | Result |
|---|---|
| Kill / rejoin verified | all 10 GONE / all 10 UP, held 180.0 s, outcome `ok`, no member skipped |
| Run | `ok`, drained (0 pending, 0 in flight at stop), metrics complete |

The 3 delegations while down are the detection gap E2b measures. Group 4 is coordinator 89's
mediocre group, so a small share after the rejoin is what the profile asks for. The campaign kills
**group 3** instead, 89's cpu-weak group, which is the best group for its ram_bound jobs (64 % of
the mix), so re-adoption has something to win.
